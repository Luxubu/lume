# Milestone 17 review corpus (m17)

30 programs written from the README and `examples/{patterns,stdlib,ownership}.lume` only, run with
`lume run`. Every expected output was worked out by hand before running; "ok" below means the
actual output matched that hand-computed expectation line for line.

Tally: **20 ok, 5 leak (2 root causes), 1 crash, 4 deliberate compile-error tests (all correct
messages), 0 wrong.**

## Ranked problems

1. **`map_values` leaks rustc E0282 whenever the block body is a method call or an interpolation on the parameter** (`{ |v| v.len }`, `{ |v| "#{v} left" }`, `{ |v| v.clamp(1, 5) }`, `{ |ss| ss.map(_.name).join("+") }`). Only arithmetic bodies (`v * 2`) pin the closure type. Hit by 4 of 8 programs that used it: `r17_list_block_methods.lume`, `r18_map_methods.lume`, `r23_grades.lume`, `r25_wordfreq.lume`. `group_by(...).map_values { |g| g.len }` is the single most natural thing to write after a `group_by`, so this will be hit constantly.
2. **A `Str` parameter `+` a string literal does not compile** (`def f(src: Str) -> Str = src + "!"` -> E0277 `str` unsized from `format!("{}{}", (*src), ...)`). Both orders, one-liners and block bodies, regardless of later use. `r24_tokenizer.lume`. This is basic and predates the milestone's features; the milestone-16 `(*src)` deref of a `&str` parameter seems to be the cause.
3. **`Int.clamp(lo, hi)` with `lo > hi` panics with Rust's own assertion text** (`min > max. min = 20, max = 5`, exit 101). `r15_num_methods.lume`. Should be a Lume message, and a compile-time error for literals like the existing `10 / 0` check.
4. **`group_by(fn_name)` is rejected while `map(fn_name)` / `map(letter)` are accepted** (`kind is a function; call it with kind()`). Inconsistent "function names as blocks" support across the new block methods. `r24_tokenizer.lume` (first draft).
5. **`capitalize` does not downcase the rest of the string** (`"hELLO wORLD".capitalize` = `HELLO wORLD`; Ruby/Python give `Hello world`). `r14_str_methods.lume`. Either change it or document it.
6. **No warning for an unreachable `match` arm** (an arm after `_`, probe p2). The exhaustiveness checker clearly has the machinery for this; a redundant `1 | 2` arm after `_` compiles silently.
7. **`[Int].avg` on an empty list returns `0.0`** silently (`r16_list_methods.lume`). Defensible, but the README lists `first`/`max`/`min` as returning `T?` for exactly this situation; `avg` on `[]` is the same case and is undocumented.
8. **The `xs[i]` is `T?` rule collides with the README's "`xs[i].method(...)` reaches the item" wording** (`r28_chains_receivers.lume`, `r29_var_fields_mut.lume`): `b.items[2].max(..)` and `q.items[0].capitalize` are errors that need `.or(..)`, while `team[0].tag("lead")` in `examples/ownership.lume` works. The error message is good, but a reader of the README will not know which form they are in until they try.
9. **Zero-argument functions must be called with `()` in expressions** (`make.uniq` -> `make is a function; call it with make()`), while the same function can be declared `def make -> [Int]` with no parens and methods with no arguments are called without them. `r28_chains_receivers.lume`. Minor, but the asymmetry between methods and functions is surprising in a Ruby-flavoured language.
10. **rustc leak messages point into `.lume/*.rs` with a 300-character single line of generated code**, which a user cannot act on (all five leak files). Since every leak in this corpus has the same two shapes, a Lume-side check (or, better, inferring the `map_values` parameter type from the map's value type) would turn them into ordinary Lume errors or into working code.

What worked notably well: every one of the 8 exhaustive-in-a-subtle-way programs compiled, the 4 non-exhaustive ones named the exact missing witness, or-patterns with swapped bindings and guards behaved correctly, inline statement blocks (including nested and map-writing ones) never failed, and `T?.map` / `T or E`.ok/.map chains produced correct output in every position tried.
